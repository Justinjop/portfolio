# 使用者手動交易的推薦規則（PICKS，2026-10-28 起）

## 流程
1. `daemon.py` 每小時 :01:30 UTC 執行 `desk.py hourly`，掃描 SignalScanner 1h 訊號。
2. 每一批新訊號都套用推薦規則，結果寫進 `desk.sqlite` 的 `signals` 表：
   - `user_pick`：是否推薦
   - `pick_grade`：推薦等級
   - `pick_rank`：在這批裡的排名
   - `batch_size`：這批的訊號數
   - `pick_version`：規則版本
3. ntfy 手機通知：每批推薦先發一則摘要，再對每個推薦各發一則附 K 線圖的通知。
4. 使用者在 Binance 合約測試網（demo）手動下單，止盈、止損、平倉都由使用者自己決定。
   - 2026-10-28 起不再使用 `journal/` 網頁日誌。
   - 每次掃描後，`testnet_sync.py` 會用唯讀 API 抓取帳戶的成交、委託、資金費和持倉，自動重建成交易紀錄，存進 `manual_trades` 表。
   - bfbot 的單（clientOrderId 開頭為 `bfT-`）會被排除。
   - 報告：`python desk.py manual`。

## 規則 P1
**排除（等級 x）：**
- 穩定幣交易對，例如 USDC、FDUSD
- ATR(14, 1h) 低於 0.2%

這兩類的來回成本約 0.2%，會吃掉全部的波動。

**排序：** 其餘訊號依 ATR% 由低到高排序。

**分級：**
- **A 級：** ATR ≤ 1.30%，全部推薦。門檻與 RULE1 相同，依據是歷史重播（`hist/`）。
- **B 級：** 如果 A 級數量不到這批可交易訊號的 ⌈n/3⌉，就用 ATR 次低的訊號補足。
- **其餘（「-」）：** 不推薦。

規則保證每批的推薦數 ≥ 1/3。

## 依據與限制（2026-10-28，hist/pick_rules.py）
**用相對排名挑前 1/3：期望值約為 0。**
歷史重播中，每小時只按相對排名挑前 1/3、以停損 + 72 小時出場：
- 主流幣：每筆 -3bp
- 山寨幣：每筆 +2bp
- 兩組按日分組的 95% 信賴區間都包含 0

**有效的是 ATR 的絕對門檻**（≤ 1.3%，RULE1）。山寨幣歷史每筆約 +20bp，但按日分組的信賴區間仍然包含 0，中位數交易是虧損。

**因此 B 級只是為了滿足「至少 1/3」的要求而補上**，預期沒有優勢。日誌會分開統計 A 和 B。

**這不是已經證實能獲利的方法。** 使用者自己管理出場，結果可能和機械出場差很多，這也是日誌要記錄、要量化的部分。

## 評估（不使用 API 金鑰，也不自動下單）
**1. 挑選規則本身：** 和使用者的執行無關。
- 用 ALLX 帳的機械出場結果（停損 2.5ATR、反向訊號、72 小時），比較所有訊號中 A、B、未推薦三組。
- 日誌「分析」頁會即時顯示。

**2. 使用者的執行：** 用 `manual_trades`（從測試網自動同步）。
- 看實際淨損益和 R（以第一張停損單計算風險）。
- 依推薦等級、出場方式（停損單／停利單／手動／強平）、多空、ATR、進場延遲、有沒有設停損、有沒有移動停損分組統計。
- MFE／MAE 和吃到的浮盈比例。
- 和同一訊號的機械出場（ALLX）配對比較。

## 修改規則的條件
- **什麼時候可以改：** ALLX 帳的已平倉訊號每多 200 筆，或日誌每多 50 筆已平倉交易，才檢討一次。
- **證據要求：**
  - 修改所依據的分組，每組至少 30 筆；
  - 方向要和歷史重播一致，或者有預先寫好的新假說。
- **版本管理：**
  - 新版本命名為 P2、P3…，寫進本檔並記錄修改日期；
  - 舊紀錄保留原本的版本標記，不回頭重新分級。
- **例外：** 為了修正明顯錯誤（例如 P1 第一天加入排除穩定幣）可以立即改，但必須記在下面的變更紀錄。
